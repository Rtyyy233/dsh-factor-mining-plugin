# 三通道送达 —— 引擎指令从策略选择器到模型眼前的三条路

**它是什么**：引擎对挖掘会话的全部驾驶指令（继续、换向、供数、收官、
义务催办、升级警告）都产自同一个策略选择器，但投放走三条路，按会话形态
各取所需：**通道一**是工具响应里的 loop 指令区——五个关键工具每次响应
必带，随调用返回；**通道二**是回合边界主动注入——会话一个回合正常结束
后静默 60 秒，引擎把当刻策略指令以用户口吻注入；**通道三**是引擎指令
文件——面向另一类宿主里"读单唤醒"式直驱会话的指令文件，每次评估后由
runner 侧重写，会话被唤醒后第一动作就是读它。三条通道同源：通道二注入
的正文与通道一 loop 区里的策略指令逐字相同，通道三是同一份 loop 数据的
文件渲染——引擎只做一次判断，投放三次。

**它的位置**：上游是引擎的停走判定与策略选择（纯函数，判定细节见
[rotate-and-growth.md](rotate-and-growth.md)），下游是三类会话形态：宿主
会话（通道一＋二）、直驱会话（通道三）、无工具面会话（一条都没有——负
情境，第七节）。

**上下游**：

| 方向 | 模块 | 关系 |
|---|---|---|
| 上游 | 策略选择器 | 三通道共用的唯一判断源（同源原则） |
| 上游 | 停走判定与推进治理 | state／义务／升级警告／策略的读数来源 |
| 下游 | 评估管线五工具 | 通道一的挂点（每次响应携带 loop 区） |
| 下游 | drive 注入器 | 通道二的投放执行（静默窗／键去重／真人优先） |
| 下游 | 直驱 runner | 通道三的写入者（消费 loop 重写指令文件） |
| 相邻 | [lane-isolation.md](lane-isolation.md) | 指令按线送达；账本绑定只管工具路由，**注入目标由矿工名册决定**（每 root 一在任者，见 drive-injector 矿工门节，0.1.26） |
| 相邻 | [scheduler.md](scheduler.md) | 灰度选点行经通道一挂入（只含事实） |

## 一、同源原则：一次判断，三次投放

- **防什么**：三条通道各说各话——工具响应说"继续"、注入说"换向"，
  模型收到两个互相矛盾的方向。
- **怎么做**：策略选择器是纯函数（同一份账本状态必然给出同一个策略与
  指令文本）；三条通道全部消费它的输出。通道一在组装响应时调它；通道二
  的注入器不自己判断，读的就是通道一同一结构的策略指令正文；通道三由
  runner 消费同一份 loop 数据渲染成文件。指令文本表（九族全文）只存一份。
- **怎么核对**：loop 区 strategy 块的 directive 字段与随后注入的正文逐字
  相同（生产转录实测在案）；why、键等遥测只在 loop 区与宿主日志出现，
  不进注入正文。

## 二、通道一：工具响应 loop 指令区（五工具挂点）

- **防什么**：会话埋头干活时收不到驾驶指令——评估一跑几分钟，等回合
  边界再注入就晚了。
- **怎么做**：五个工具的每次响应必带 loop 对象——状态查询、单因子评估、
  批量评估、轨迹汇总、入册提交；组合评估的轮询结果同样携带（走评估族
  路径）。挖矿会话每回合通常触发多次（评估、轮询、查状态），指令随每次
  调用免费送达。
- **送什么**：一块驾驶舱仪表＋方向盘——state（值域两态：running＝
  必须继续内循环；must_rotate＝必须换向。may_stop 已随 2026-10-03
  永续化退役——除死线与用户指令外无终态，引擎不再发"允许收尾"）、
  义务句（上一轮自己声明的下一步假设被回显成义务，或停笔宣言的
  拒收理由）、族饱和分级警告、
  策略块（类型／为什么／键／指令正文）、尾部线遥测与近失清单、推进治理
  遥测（距上次增长秒数、已发换向数、政策原文）、推理日志指针、并行线
  注记；条件块按需出现（调度器遥测只在开关打开时、基础设施失败纠偏块
  只在近 30 分钟有超时记录时）。近失＝折减后 p 值落在 0.05 到 0.30
  之间、没过入册线但值得再深挖的候选。逐字段触发条件的全表见模型可见
  上下文盘点卡 F-DSH-03（全套卡与指令全文收录在仓库
  docs/model-context/f-dsh.md）。
- **边界**：loop 区只在引擎侧账本存在时才有意义——未绑定账本的会话连
  工具调用都被首调门挡住，自然看不到 loop 区。
- **不过怎么办**：state=running 而模型停下来等指示＝违规（停走纪律见
  [mining-never-stops.md](mining-never-stops.md)）。

## 三、通道二：回合边界主动注入（六族＋静默窗 60 秒）

- **防什么**：会话写完总结就停笔等指示——历史上用户一晚手动推了 31 次，
  注入器就是这 31 次人工推动的机械化。
- **怎么做**：会话的一个回合以正常完成结束后，引擎的 loop 状态仍是
  running 或 must_rotate 且带策略 → 先等 60 秒静默窗（给真人先说话的
  窗口），窗内无真人消息则注入一条策略指令。指令按触发条件分六族：
  **continue**（惯性延续——执行上一轮声明的假设）、**rotate**（换向——
  查已试路径、从未覆盖的维度构造新假设；超时换向另有全幅文本）、**随机
  兜底**（无路可走的标准出口——生成随机因子找灵感，幸存者逐个走标准
  管线）、**compose**（中阶合成——已验证未入册存量充足时构造正交组合）、
  **drain**（机械库存清空时的供数指令——随机优先论文次之）、**死线收官**
  （死线到点的一次性收官指令）。各族全文与触发条件见盘点卡 F-DSH-04；
  通道二自身的投放护栏（键去重、楔死恢复、兜底扫描）见
  [drive-injector.md](drive-injector.md)。
- **阈值**：静默窗 60 秒（用户拍板：给人先说话的窗口）；continue 与查询类
  同键重推不限次（2026-10-03 起"连续 5 次"上限已删除——永续纪律；防复读
  由引擎侧三原语层承接：同一欠账三次重申未消账→升级告警并继续推，见
  [three-primitives.md](three-primitives.md)）。
- **不过怎么办**：真人消息取消待发注入；忙碌会话不注入
  （楔死恢复是唯一例外）。

## 四、通道三：引擎指令文件（面向直驱会话）

- **防什么**：直驱会话（另一类宿主里被定时唤醒、按指令执行器的会话）
  没有工具响应与回合注入两条腿——指令必须落成文件，唤醒时才有得读。
- **怎么做**：runner 侧（直驱脚本的驱动器）在每次评估后消费引擎的 loop
  数据，重写账本根目录下的指令文件：首行声明"本文件每次评估后重写，
  唤醒后第一动作＝执行下列指令"；正文为策略／义务的文本渲染＋深化战役
  与队列点名＋同一份 loop 数据的原始块（机器可读）。会话被唤醒的第一
  动作就是读它，完成一条在回执区记一行。文件样张与机制见盘点卡
  F-DSH-12。
- **边界**：这条通道只在直驱跑批时存在——不跑直驱，账本根目录下就没有
  这个文件（生产查证在案）。**宿主会话看不到它**：即使直驱夜跑与宿主
  会话并行共用同一账本，宿主会话也不会因此看到任何额外文本——宿主侧
  的引擎触达仅经通道一与通道二。

## 五、注入身份纪律：去引擎标识、用户口吻

- **防什么**：模型把注入消息当"可吸收的机器通知"——等待环叙事吸收
  换向指令的实录（六连发全被吸收）证明，带引擎标识的消息会被打折。
- **怎么做**：注入正文就是策略指令本身——无前缀、无依据尾注，消息身份
  标为用户。溯源不丢：为什么、键、注入时刻全部保留在工具响应的 loop 区
  与宿主日志里，只是不进模型眼前。收官指令同理（用户口吻的收官命令）。
- **边界**：真人消息永远优先——静默窗、取消待发、连注清零三件护栏都
  为此存在；注入与 loop 策略同源，模型不需要再确认。

## 六、桌面路径（2026-09-30 修复后）：注入器只由预置行持有

- **防什么**：两个注入器实例对同一会话双注——注入键去重是实例内内存
  态，跨实例无效。
- **背景**：桌面宿主给会话加预置（预置的封闭清单决定会话看得见哪些
  工具），而工具包此前只注册在全局树、不在任何预置清单里——桌面会话
  看不到任何因子工具，三条通道全部失效（详见失败样例与
  [lane-isolation.md](lane-isolation.md) 的负情境）。修复在配置层：按预置
  注册表的官方机制，在桌面配置里整段重申两个预置的插件清单并各追加
  工具包行。
- **注入器归属收口**：全局工具行设"注入器关闭"开关（保留工具注册，
  不给注入器），注入器只由预置行持有一个——桌面注入器恰好一个，且
  活在挖矿会话所在的预置域内；死线工具走预置行注入器，行为不变。
- **边界（如实记录）**：整段覆写不随上游升级自动合并——升级后须重对
  标准清单；恢复的旧会话工具面不追溯刷新，修复只对新建会话生效。

## 七、通道覆盖矩阵与负情境

| 会话形态 | 通道一 | 通道二 | 通道三 |
|---|---|---|---|
| 宿主会话（工具面在） | 有 | 有 | 无（看不到指令文件） |
| 直驱会话（读单唤醒） | 无 | 无 | 有 |
| 无工具面会话／纯命令行直驱 | 无 | 无 | 无 |

负情境与正向情境同权重：**模型看不到任何引擎指令**不是空集无害，而是
全部治理（停走纪律、多重检验可见性、死线）同时失效的静默失效态——引擎
本体与账本照常活着，试验计数与门槛在后台继续演进，双方状态互不可见。
判别"会话为什么自停"先查工具面在不在（盘点卡 F-DSH-13 的对照实测），
再查引擎判停。

## 成功样例：三通道同源的一次实测对账

2026-09-30 桌面修复后的首个会话走通全链：首调门拒绝原文 → 账本声明
回执（回执自带 loop 区，策略是入册满 45 只触发的里程碑正交审计指令）→
60 秒静默窗后 continue 注入送达（间隔 61 秒，正文与指令文本表逐字相同、
无引擎标识）→ 会话进入 65 分钟自主挖掘，评估间隔超窗时 loop 区的策略块
换成超时换向全幅文本（同源纪律：先出现在 loop 区，注入器随后投放）→
两只候选入册。同一份判断在工具响应、注入、（如直驱并行）指令文件三处
逐字一致——这是同源原则的活体证明。

## 失败样例：注入消失（2026-09-30 桌面迁移断链）

桌面前端部署插件当夜起，挖掘会话与注入器断链：桌面会话的工具面被预置
过滤剥掉（工具包不在预置清单），一个纯命令行直驱的挖掘会话真挖了一小时
后自停等口令——三条通道一条都够不着它：没有工具调用就没有 loop 区；
注入器以"会话内出现过因子工具调用"为武装条件，对它永远不可见；指令
文件只在直驱跑批时存在。恢复旧会话也不热挂（工具面不追溯刷新）。
根因两层：预置清单缺工具包行＋版本兼容门把服务行禁用（同夜查明，配置
层修复）。教训入档：送达链的完整性以"会话实际看得见什么"为准，不以
"引擎活着"为准——引擎活着只是静默失效的伪装。
