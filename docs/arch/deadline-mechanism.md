# 死线机制 —— 连续挖掘的最低期限、一次性收官与跨重启生命周期

**它是什么**：用户说"这个会话挖到早上八点"时，这句话变成一个可执行的
机器状态：死线武装后，停止条件由墙钟接管；到点注入**一条**收官指令
（汇总战果、不再开新试验），随后对该会话解除自动推进、交还用户。
2026-10-03 生命周期修订后死线是**会话级＋跨重启持久**的：粒度按会话
（"这个会话挖到八点"，并行会话不连坐）；死线与收官标记落盘插件侧
状态文件，宿主重启后未来死线重新武装、已过期死线自动取消并静默交还
用户。核心语义不变：**死线是最低工作期限，不是收摊点**——到点之前，
停走的决定权在死线与用户手里，模型无权自停，任何"转入监控／保持／
等待"的自我收官都违规。

**它的位置**：宿主注入器的运行时状态＋插件侧落盘文件
（`~/.dsh/factor-drive-state.json`，与 bindings 伴生）；经一个会话内
工具（三态：设／清／查）由模型按用户口述操作——用户不碰配置文件、
不重启。上下游：上游是用户口述的时刻，下游是注入器的收官投放与
告警层。

**上下游**：

| 方向 | 模块 | 关系 |
|---|---|---|
| 上游 | 用户口述 | 死线唯一合法来源（模型不得自行推测时刻） |
| 上游 | factor_drive_deadline 工具 | 会话内设置／清除／查询的唯一入口 |
| 下游 | drive 注入器 | 死线接管保险丝；收官注入由它投放 |
| 下游 | 宿主日志 | 迟到告警（不进模型上下文） |
| 相邻 | [rotate-and-growth.md](rotate-and-growth.md) | 死线期内卡住照常超时换向 |
| 相邻 | [mining-never-stops.md](mining-never-stops.md) | 死线前静默即违规的总纪律 |

## 一、方案 B 的定调：最低期限，非收摊点

（"方案 B"是设计档案里这套机制的方案名——把死线从配置文件操作改成
会话内工具操作的那个方案，出身见第八节。）

- **防什么**：两种相反的失败——无死线时模型自行停笔等指示（历史上
  用户被迫一晚手动推 31 次）；有死线时模型提前"自我收官"（转监控态
  等到点）。定调：死线只回答"至少挖到几点"，不回答"什么时候可以
  偷停"。
- **怎么执行**：武装后死线接管停止条件；**连续注入不设上限**（2026-10-03
  起「连续简单注入 ≤5 次让位真人」分支删除——上限让位专咬无死线日间
  挖掘，防复读护栏移交引擎侧）；死线期内一切停走纪律照常——卡住照常
  超时换向（见 [rotate-and-growth.md](rotate-and-growth.md)），穷尽宣告
  照常不当结论收。
- **不过怎么办**：模型在死线前转入等待态＝违规，换向指令会持续重推
  直到有评估落账（全幅指令文本明写此句）。
- **会话级粒度**（2026-10-03 拍板 D1）：死线按会话生效——"这个会话
  挖到八点"的语义正确形态，双线并行时另一条线不连坐；状态文件按
  会话记录收官标记。

## 二、收官：到点一次，注入后解除

- **怎么执行**：注入检查发现墙钟已过死线 → 先给会话做一次持久化检查点
  → 注入一条收官指令（用户口吻："死线已到（时刻）。立即收官，不要再
  发起新试验：汇总本会话的试验数／入册／近失与账本状态，写一份收官
  战报后结束。"）→ 该会话标记收官完成（`finished`，落盘——**防双发**：
  收官即落盘，重启后已 finished 的会话不再发第二次收官注），自动推进
  对其解除。真人消息仍然有效——解除的只是自动注入；**收官或取消后，
  用户的一条真实消息＝重新接管授权**（2026-10-03 拍板 D2，过期死线
  一并解除——防"再收官循环"：否则每次收官都要手动 clear）。武装
  回执、收官指令、错误与查询文案的逐字文本见盘点卡 F-DSH-06
  （docs/model-context/f-dsh.md）。
- **边界**：收官检查排在忙碌守卫之后（评估跑完的会话不被打断）、排在
  引擎状态查询之前（收官不依赖停走状态）。重新设置死线会重新武装
  会话——连挖两段是合法用法。

## 三、三态工具与时刻纪律

- **设置（set）**：把用户口述时刻换算成 ISO 8601 本地时区调用。非法
  时刻返回原文与格式示例（"无法解析时刻……需要 ISO 8601，如
  2026-09-18T08:00"）。设置时可顺带指定兜底巡检间隔（缺省 5 分钟）。
- **清除（clear）**：提前收工——解除死线＋清全部会话收官标记（落盘），
  恢复常规自动推进（连注不限，防复读护栏在引擎侧）。
- **查询（query）**：不带参数调用即查——回执含死线标签与毫秒值、已
  收官会话数、巡检间隔、楔死阈值与楔死会话清单、每会话活性／注入
  年龄／代理缺失计数、无法送达名单（诊断面详见
  [drive-injector.md](drive-injector.md) 第六节）。未设死线时说明字段
  写明"常规自动推进（无死线；连注不设限）"。
- **"用户明确说出的时刻才是死线来源"**：模型不得把"挖久一点""挖到
  没想法为止"换算成自行推测的时刻——那不是死线，是擅自替用户定
  停走权。

## 四、钟点语义定调：午夜后的"明天早上"＝当天早上

- **防什么**：凌晨开工的夜跑，"明天早上八点"被按日历字面换成隔日
  早上——死线凭空多出一整天。
- **定调**：午夜后说"明天早上八点"，指**即将到来的当天早上**，不是
  日历上的次日。说话人在凌晨零点二十分说的"明早"，意图显然是几小时
  后的这个早上。
- **案底**：一次夜跑 00:05 开局，用户本意死线当天 08:00，被换算成次日
  08:00——会话多挖一整天，收官由用户口头纠正。此后定调与换算纪律
  一并写进工具描述：换算拿不准时，在响应里报告换算结果再执行，不
  静默猜。

## 五、迟到告警：宿主日志，不进模型

- **防什么**：死线过了、收官注没送到、没有任何人知道——"死线必达"
  在插件面内的现实形态是**必告警**（送达保证需要宿主配合）。
- **怎么查**：兜底扫描每轮核对：死线已过而该会话未收到收官注 → 每
  30 分钟一条告警（会话尾号＋迟到分钟数＋可能原因：代理缺失／楔死／
  收件箱受阻），独立于注入检查的一切早退形态。验收纪律同源："收官注
  按时到，或日志出现告警——不允许第三种沉默。"
- **边界**：告警只进宿主日志——它是给操作者排查送达链用的，进模型
  上下文只会教模型"替引擎操心送达"。

## 六、落盘与重启生命周期（2026-10-03 修订，逆转"重启即失"）

- **是什么**：死线不再是一次性内存态——落盘到插件侧
  `~/.dsh/factor-drive-state.json`（与 bindings 伴生，职责分离：挖掘
  语义落引擎侧，会话持续语义〔绑定＋死线＋收官标记〕落插件侧；原子
  写＝临时文件＋改名）。schema：`{version, deadline:{iso, epochMs,
  label, setAtMs, setBy}, sessions:{<id>:{finished, finishedHow:
  "wrap-up"|"restart-cancel"}}}`。
- **重启加载**：死线在未来 → 重新武装（到点照常收官，含会话未打开
  场景——auto-resume 物化送达）；死线已过期 → **自动取消**：不补
  收官注、不恢复常规推进，种子名单内会话全部标记
  `finished(restart-cancel)`，fileLog 记 `deadline-cancelled-on-restart`，
  此后对它们一律静默（不注入不收官不推进）——手动使用不受限。设计
  理由：重启后补发一条"几小时前就该收官"的注没有信息价值，静默交还
  用户才对；而过期时刻若被当现役死线恢复，等于替用户延长了授权。
- **重新接管授权**：收官或取消之后，用户的一条真实消息＝重新接管
  （常规推进恢复；过期死线一并解除）——没有这条，每次收官都要手动
  clear，"防再收官循环"。
- **clear 语义**：清死线＋清全部会话的 finished 标记＋落盘——提前
  收工的完整出口。
- **合流总规则**（注入器每轮判定）：引擎 loop 活（running/must_rotate）
  ∧ 插件侧未收官/未取消 → 自动推进；任一停 → 静默。恢复序：bindings
  种子 → drive-state（死线/收官）→ 引擎 status → 合流。

## 七、武装回执：一眼可读的诊断面

设置与查询的回执携带同一组状态字段：死线标签与毫秒值；已收官会话数；
兜底巡检间隔；楔死阈值与当前楔死会话清单（尾号）；在册追踪会话总数；
逐会话行（距上次事件时长、上次注入的键与距今时长、代理缺失计数、
是否已收官及收官方式）；无法送达名单。回执的说明字段写明当前语义：
"死线某某时刻（会话级、跨重启持久）：到点注入一次收官后自动解除；
重启时已过期则自动取消并静默交还用户"或"未设死线：常规自动推进
（无死线；连注不设限）"。设计
意图：死线状态与送达健康在同一份回执里——设了死线的人（模型）和
排查送达的人（操作者）都不用去读引擎内部账。

## 八、出身与近邻：从配置文件到会话内工具

- **出身**：死线最初是宿主配置项——夜跑前用户改配置、带补丁重启，
  早晨再改回来。方案 B（2026-09-17 拍板）把它变成会话内工具操作：
  模型按用户口述随时设置、清除、查询，配置项只作为初始武装保留
  （写错时刻只记一次日志并解除）。方案命名沿袭同期部署：方案 A 是
  并行线隔离（见 [lane-isolation.md](lane-isolation.md)），方案 B 是
  本机制——两者共同构成"多会话连续挖掘"的运行时底座。
- **与调度视界的关系**：调度器有自己的时间视界（默认 7 天，视界内
  "至少一次成功"概率过低的节点退场进孵化——停车但可重返）。死线
  管的是**会话这一夜挖到几点**，调度视界管的是**一个研究方向还值
  不值得继续下注**——前者是墙钟纪律，后者是边际价值判定，互不管
  对方的时段（见 [scheduler.md](scheduler.md) 第二节）。

## 成功样例：一次教科书式收官（2026-09-30 验收）

模型在会话内设置一个已过时刻的死线 → 回合结束 → 61 秒后收官注入送达
（正文即收官指令、用户口吻、无引擎标识）→ 74 秒后模型交出收官战报
（试验数／入册／账本状态汇总），自动推进解除。从设置到收官战报全程
105 秒，设置回执、收官时刻、解除留痕三层都在宿主日志可查——死线机制
与注入链在修复后的桌面宿主上完整闭环。

## 失败样例：死线迟到 4 小时 19 分（2026-09-29）

死线 09:00，两个会话的收官注 13:19 才送达。取证三层：收官注的时间戳
与"用户消息回合结束后 60 秒整"的特征吻合——不是死线机制触发，是
真人中午回来发消息恰好走通了事件路径；引擎侧换向记账冻结在第一注，
证明凌晨起自动推进就停了；根因在送达层——对空闲会话只有 5 分钟兜底
扫描一条腿，而扫描从凌晨 3 点 20 分起不再送达（宿主回收会话，最早
一道门零日志静默返回）。修复三件：代理缺失告警（计数＋30 分钟节流，
"告警有无"成为判别宿主回收与定时器死亡的一锤定音信号）、死线未送达
  告警（第五节）、诊断面扩展。教训入档：**死线的敌人不是没设，是设了
  却没人知道没送到**——一次性状态的送达链必须自带"没送到会喊"的
  能力。
