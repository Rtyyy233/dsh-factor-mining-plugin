## 一、总对照：两套系统 × 三种宿主

| | 因子挖掘系统 | 投研系统（bull-case-anatomy） |
|---|---|---|
| 嵌入路线 | **插件栈全嵌**——四个 npm 包装进宿主进程 | **预置+外挂 CLI 半嵌**——宿主里零插件包，引擎是仓库里的独立命令行程序 |
| 引擎进程 | 宿主内常驻：服务包管理一个 Python 桥子进程，桥再管评估 worker | 无常驻进程：会话每次执行引擎命令、命令跑完即退 |
| 模型触面 | factor_* 工具面（40 件工具）+ 回合边界自动注入 | 普通 shell 工具跑引擎命令 + 技能壳两枚 |
| 指令送达 | 推送式三通道（见第四节） | 拉取式（命令回执、工作单、状态门，见第六节） |
| 状态 | 账本根目录（用户主目录下，插件配置指向） | 全部在投研仓库（账本/审计态/轨迹页），宿主零状态 |
| 宿主形态 | web 宿主、桌面宿主两种（第节三）；zcode 直驱是第三形态（第七节） | web/桌面经预置半嵌；zcode 直读仓库（无预置，靠会话纪律） |

**三种宿主**：①web 宿主（`dshweb` 命令起的 Node 服务，浏览器用）；
②桌面宿主（Electron app）；③zcode（终端编码代理，完全不经 DSH 宿主）。
web 与桌面共用同一套插件包，差异在配置层（第三节）；zcode 是嵌入的反面
参照（第七节）。

## 二、装了什么：因子挖掘的四个包与各自角色

四个 npm 包，源码在本仓库 ts/ 目录，打包成 tgz 后装进宿主 profile：

| 包 | 角色 | 失败时什么样 |
|---|---|---|
| `@deepseek-ai/dsh-factor-mining` | **服务包**——能力中枢。向宿主上下文注册 `ctx.factorMining` 服务对象；管理 Python 桥子进程的生命周期；承载双账本配置（stateRoot/extraRoots） | 服务行被禁用或装载失败时，依赖它的工具行会连坐（预置激活审计拒绝挂载整个预置） |
| `@deepseek-ai/dsh-factor-mining-python` | **Python 桥包**——按服务包的配置拉起 Python 引擎子进程（桥），桥单线程承接全部会话的因子调用，桥再派生评估 worker 子进程 | 桥起不来=所有 factor_* 调用报错；桥活着但 worker 冻结=调用假死（历史上有过 worker 继承输入管道导致冻结的事故，已修） |
| `@deepseek-ai/dsh-tool-factor-mining` | **工具包**——模型看得见的 factor_* 工具面（约 40 件：状态查询、评估派发、批量评估、轨迹汇总、入册提交、账本声明、死线设置等），以及**回合边界自动注入器**（drive 注入器，通道二的执行体） | 工具不在会话工具面=模型根本不知道引擎存在（2026-09-30 桌面事故的断点，见第三节） |
| `@deepseek-ai/dsh-factor-mining-bundle` | **组合件**——自身几乎无代码，它的作用是带一段配置（cordis.patch.yml），把上面三个包组装成宿主组合树里的两行：`factor-mining`（服务行）+ `tool-factor-mining`（工具行）。profile 的 package.json 里挂 bundle 一个名字，等于三件套全装 | bundle 没挂=三件套都不在 |

Python 引擎本体（评估、多重检验墙、账本、策略选择）不在任何 npm 包里——
它是一棵独立的 Python 源码树，以 `pip install -e` 可编辑方式装进系统 Python
（见第八节部署路径）。桥只是它的进程入口。

## 三、装在哪：profile 目录与组合树

### 3.1 profile 目录

每个宿主一个 profile 目录（`~/.dsh/profiles/web/`、`~/.dsh/profiles/desktop/`），
里面四样东西：

- `package.json`——**包清单**：dependencies 列 tgz 文件引用（`file:pkgs\xxx.tgz`），
  `dsh.profile.bundles` 列要装载的 bundle。宿主启动时按它装包。
- `pkgs/`——tgz 实体存放处。
- `cordis.patch.yml`——**用户补丁层**：对组合树按行 id 做覆写/追加（下文）。
- `cordis.yml`——宿主每次启动再生成的脚手架文件（空表头+注释），不是配置
  载体，别改它。

### 3.2 组合树：三层叠加，逐层覆盖

宿主启动时把所有配置来源合并成一棵"组合树"（每行有 id，后层按 id 覆盖
前层）：

1. **bundle 层**：每个 bundle 自带的 patch（因子 bundle 插入服务行+工具行）。
2. **用户 patch 层**：profile 的 `cordis.patch.yml`——持久配置改这里。
3. **临时外挂层**：启动参数 `dsh --patch <文件>`——惰性文件、不进 profile、
   不传参不生效、隔夜即弃。历史用法是"解除连注上限+设死线"两件事；2026-10-03
   后连注上限已删除、死线改为会话级工具设置并落盘（见第五节），外挂层的
   通宵用途收窄为兼容旧跑法的备用通道（新跑法不再需要它）。

诊断组合树实况的命令：`dsh --profile <名> --dump-config`（桌面 profile 被
Electron 独占时，复制一份 profile 别名后对副本 dump——这是桌面侧的标准
静态审查通道）。

### 3.3 agent preset 封闭清单：全局注册不等于会话可见（09-30 事故的教训）

这是全篇最容易误判的一层，单独立节。

**机制**：桌面宿主给每个新会话加入一个 agent preset（会话头部 `agentPreset`
字段记录归属）。**会话看得见哪些工具，由预置定义里的封闭插件清单决定**
（`presets/standard.patch.yml` 里的 plugins 列表）——工具包注册在全局组合树
上，不等于任何会话能看到它。web 宿主没有默认预置行，全局注册的工具直接
可见——这正是两宿主的实质差异。

**事故**（2026-09-30，已修复）：桌面前端部署插件当夜起挖掘会话全哑。两层
根因：①工具包只注册在全局树，不在任何预置清单里——桌面全部会话（无论
standard 还是 comprehensive-investment 预置）看不到任何 factor_* 工具，三条
指令通道一条都够不着会话；②桌面宿主运行时升级到 0.2.0 后，Python 桥包
声明的兼容版本范围不覆盖新宿主版本，兼容门把服务行也禁用了——"服务层
正常"的早期判读被证伪（当时探测到的只是兼容探测，不是服务激活）。

**修复后现状**（全部在 profile 配置层，零包改动）：

- 用户 patch 层**整段重申**两个在用预置（standard 与 comprehensive-investment）
  的插件清单，并在清单末尾各追加工具包行——预置持有工具面，桌面会话
  可见了。
- **注入器归属收口**：全局工具行设"注入器关闭"（保留工具注册供 CLI/无预置
  上下文使用），注入器只由预置行持有一个。若全局行与预置行各跑一个注入器，
  两实例对同一会话都会响应（去重表是实例内内存态，跨实例无效）→ 双注。
  收口后桌面注入器恰好一个，死线工具照常工作。
- web 侧零触碰（它本来就没这层问题）。

**已知边界（如实记录）**：整段覆写不随上游 bundle 升级自动合并——上游升级
后 standard 清单若有变化，须重对重申段；桌面还有三个预置（minimal/ptc/cordis）
未加工具行，选它们开挖矿会话仍然没有工具面；**恢复的旧会话工具面不追溯
刷新**——修复只对新建会话生效，重启后须开新会话。

### 3.4 peer 兼容门与精确版本豁免

宿主装载插件时校验插件声明的宿主版本范围（peer 依赖）：不满足→装载器
**禁用该行**并打告警——不是报错崩溃，是静默降级，所以容易被误读成"没
装但也不碍事"。逃生门是官方命令 `dsh plugin --profile <名> allow-version
<包@版本> --dsh-version <宿主版本> --accept-risk`，豁免记录落在 profile 的
`compatibility.json`（当前桌面 profile 有一条：Python 桥包 0.1.4 对宿主
0.2.0-rc.2 的精确豁免）。**正道**是插件包升版本、把兼容范围放宽后重打
tgz（挂账事项）；豁免是过渡手段，每条豁免都是一笔显式登记的风险。

## 四、指令怎么送达：三通道在宿主侧的物理实现

引擎对挖掘会话的全部驾驶指令产自同一个策略选择器（纯函数），投放走三条
通道——一次判断，三次投放，文本同源：

| 通道 | 物理形态 | 谁触发 | 模型看到的身份 |
|---|---|---|---|
| 一：loop 指令区 | 工具响应内嵌对象——五个关键工具（状态查询/单因子评估/批量评估/轨迹汇总/入册提交）每次响应必带：状态（值域 {running, must_rotate}——may_stop 已于 2026-10-03 退役，收尾只由死线收官或用户指令触发）+义务句+族饱和警告+策略块+近失清单+遥测 | 会话每次调用这些工具 | 引擎数据（模型自己读） |
| 二：回合边界注入 | **drive 注入器**（工具包内的常驻组件）：会话回合正常结束后先等 60 秒静默窗（给真人先说话），窗内无真人消息→把当刻策略指令以**用户角色消息**注入。护栏：策略键去重（同键不重发；2026-10-03 起连注≤5 上限已删除，防复读由三原语层的"同一欠账连推三次未消账即升级告警"承接）、真人消息取消待发、楔死恢复（运行中零事件 30 分钟→取消死回合→收敛后重推）、兜底扫描每 5 分钟常开 | 回合结束边沿+扫描时钟 | **用户消息**（无引擎标识——带引擎标识的指令会被模型打折，这是 2026-09-19 等待环事故的定论） |
| 三：引擎指令文件 | 账本根目录下的指令文件，直驱 runner 每次评估后重写；会话被唤醒后第一动作就是读它 | 直驱 runner（不在宿主进程内） | 文件内容（模型主动读） |

**通道覆盖矩阵**（负情境与正向同权重）：

| 会话形态 | 通道一 | 通道二 | 通道三 |
|---|---|---|---|
| 宿主会话（工具面在） | 有 | 有 | 无（宿主会话看不到指令文件） |
| zcode 读单唤醒直驱 | 无 | 无 | 有 |
| 纯命令行直驱（无唤醒无读单） | 无 | 无 | **无——全部治理静默失效** |

最后一行是事故高发区：引擎与账本照常活着、试验计数与门槛在后台继续
演进，但会话与引擎状态互不可见——"引擎活着"只是静默失效的伪装。判别
"会话为什么自停"永远先查工具面在不在（盘点卡 F-DSH-13），再查引擎判停。

## 五、状态放在哪：因子挖掘侧

| 状态 | 位置 | 重启后 |
|---|---|---|
| 试验账本/入册账本/派生图/审计计划 | **账本根目录**：插件服务行配置 stateRoot 指向（生产=个股线 `~/.factor-mining-stock-h10c30`）；第二账本走 `extraRoots`（生产=ETF 线 `~/.factor-mining`）。双账本=两套独立试验计数，计价各算各的墙 | 持久，无损 |
| 会话↔账本绑定表 | `~/.dsh/factor-session-bindings.json`（会话→账本键值表，原子写、有界 500 条） | 持久——路由与注入器扫描名单从它重建，重启免手动唤醒 |
| 审计随机种子 | 账本根 `audit_state/`；对模型禁读（防挑安全进度应付） | 持久 |
| **死线时刻** | **落盘**：`~/.dsh/factor-drive-state.json`（2026-10-03 起，与绑定表伴生；重启不丢；重启时已过期的死线自动取消并留痕；用户一条真实消息=重新接管授权） | 不丢——仅过期自动取消 |
| 注入键去重表/待发定时器 | 注入器内存态 | 丢——同键可能重发一次；扫描名单从绑定表重建兜底（连注计数已随 2026-10-03 上限删除而退役） |
| 桥与 worker 进程 | 内存 | 重启即重拉 |

## 六、投研系统：预置+外挂 CLI 半嵌

### 6.1 装了什么：宿主里零插件包

投研引擎是投研仓库 `modules/investment/research/bull-case-anatomy/` 下的
Python 命令行程序（`research/engine/` 全目录），**没有常驻进程、没有 npm
包、没有桥**。模型（会话）用普通 shell 工具执行引擎命令，命令输出就是
模型看到的一切——引擎内容只经"命令输出"这一条物理通道回流。

### 6.2 预置承担的三件事

桌面/web 会话若选「全景投研」预置（comprehensive-investment，@local 预置包），
装载三样东西：

1. **persona 系统级人设**——预置里 persona 插件的 config.prefix 模板，宿主
   每轮组请求时渲染注入：投研根路径与调用姿势（bash 每次新 shell 须先 cd）、
   冷启动先读仓库 AGENTS.md、四条铁律（三权分离/默认档开工/研报给人读/
   前瞻推演先行）、收工纪律（推进到引擎报"无下一步合法动作"才收工）。
2. **技能目录绝对补挂**——预置的 skill-filesystem 插件配置 `customSkillDirs`
   指向投研仓库内的技能目录（绝对路径）。为什么必须补挂：DSH 的项目根=
   git 根，默认技能发现找不到 git 根深处的投研技能；补挂后两枚技能壳
   （engine-status 正向状态视图、quant-discipline 量法纪律）才出现在会话
   技能清单里。技能正文不自动注入，调用时全文进上下文。
3. **冷启动读仓库纪律文件**——投研根 AGENTS.md（引擎协议、账本规矩、
   禁读区）+ git 根的重定向桩（会话常从 git 根启动，桩把投研会话指到
   投研根并要求先 cd）。

负情境：未选该预置的会话，这三样全无——对它而言投研引擎只是磁盘上一个
陌生的 Python 脚本。

### 6.3 指令怎么送达：全部拉取式，无注入通道

投研引擎从不向会话推送任何东西。引擎需要会话知道的事，全部嵌在**会话
自己执行的命令的输出**里：

- **引擎回执**——status 视图/成功回执尾部提示/被拒时的拒绝文案（拒绝即
  教学：文案写明出路命令）。
- **工作单两拍**——引擎需要模型意见的仪器（组合读数/摧毁重放/盲读/法庭
  重喂）拆两步：第一拍引擎导出提示词文件、打印 PENDING 指引、停住；
  会话以隔离子代理逐条作答写成回复 JSON；第二拍原命令带 `--replies-file`
  回填续推（盘点卡 T-DSH-05）。
- **审计议程**——随机审计点是保密抽定的；会话每阶段跑 `check --progress`
  越过抽中点才返回 AUDIT 指令；交付门反逼（审计未完成不能交付）。种子
  在 verify-complete 才揭示入账（盘点卡 T-ZC-03）。

与因子线的对照：因子线的引擎会**主动**在回合边界找会话（通道二注入），
投研线的引擎只**应答**——两条线的"引擎驾驶权"设计取向完全不同，前者
是无监督长跑（停走纪律+死线），后者是人在环的深研工序（每步由会话发起）。

### 6.4 状态放在哪：全在仓库，宿主零状态

研究线账本（`research/ledger/*.jsonl`，append-only 带哈希链）、审计态
（`research/audit_state/`）、轨迹页（`research/trail/`）、审计观察名单、
合同——全部是投研仓库里的文件。换宿主、换机器（带仓库）无缝接续；
DSH 宿主对投研系统唯一的"状态"就是预置配置本身。

## 七、zcode 直驱：嵌入的反面参照

**形态**：ZCode（终端形态的编码代理，会话与数据在用户目录 .zcode 下）里
的会话**不经 DSH 宿主**：模型直接在命令行启动 Python 桥进程（引擎的命令行
入口），发 JSON-RPC 请求驱动评估/入册/日志全部功能。2026-09 起这条线承担
通宵无人值守挖掘，是当月主力生产方式。**没有任何插件、没有预置、没有
工具面**——模型看见的是：factor-mining 技能纪律全文（用户级技能根）、
开场白（声明账本与死线）、引擎命令的 stdout/stderr、定时唤醒的 prompt
（盘点卡 F-ZC-01 至 F-ZC-04）。

**注入器不可见的负情境（设计边界，如实写）**：注入器的武装条件是"会话内
出现过 factor 工具调用"——zcode 直驱会话不走宿主工具面，**对注入器永远
不可见**；loop 指令区跟着工具响应走，它也没有。三通道里它只有通道三
（读单唤醒：runner 每次评估后重写指令文件，会话被定时唤醒后第一动作读它）。
若连定时唤醒都没有（纯命令行直驱），则三条通道一条都不剩——下一小节的
事故就在这里发生。

**自停边界事故实录**（2026-09-30 深夜）：桌面宿主因第三节的两层根因没有
工具面，一个本该走 factor_* 的桌面会话退化成命令行直驱——它真挖了一个
多小时、有真实评估落账，然后自停，输出"说继续"等口令。宿主的会话驱动
对它完全失明：注入器看不到它（无工具调用史）、事件路径等不到它的回合
（它的"回合"是桥进程调用，不产生宿主会话事件）。这正是"嵌入"的边界
讨论的活体案例：**驱动通道的覆盖面以"会话与宿主之间的可见约定"为界**——
绕开宿主约定的会话再勤奋，也在治理真空里。后续处置已挂账（推荐方案：
引导层——直驱会话的开场纪律优先走宿主工具面；看门狗方案暂缓）。

**通宵操作法**（这条线的正确姿势）：现在只需在会话里用工具设死线（落盘、
重启不丢、过期自动取消）并给开场白声明账本；历史上的"①外挂层启动
（解除连注上限+设死线）②开场白让会话调到 factor_* 工具（哪怕一次状态
查询——注入器即武装）"两步法是 2026-10-03 前的形态，其"让会话调到工具"
这半步仍是注入器武装的关键（不走工具面的直驱会话对注入器不可见）。
纯 zcode 无宿主的夜里，仍用 zcode 自己的定时任务做读单唤醒（指令文件
通道），并在开场白里写死死线与账本。

## 八、部署与升级真路径

**TS 侧（四包）**：改 ts/ 源码→esbuild 打 bundle→npm pack 出 tgz→拷进目标
profile 的 `pkgs/`→改 profile `package.json` 里的版本号→重启宿主（重装只认
版本号变化——**不改版本号=不重装**，这是最容易踩的坑）。web 与桌面两个
profile 各自独立装，升级哪边拷哪边。

**Python 侧（引擎）**：不走 tgz——系统 Python 以 `pip install -e` 可编辑
方式**直接指向主仓库源码树**。部署=改动 cherry-pick 落主仓库 main 分支
即生效（下次进程重拉时）；桥重启才吃到新代码。

**重启语义**：web 宿主重启必须走 `dshweb` 包装命令（自带代理环境变量+
stderr 捕获+启动时间戳——2026-09-20 有过裸重启丢代理、当夜论文检索全灭
的事故：终端历史里存的裸命令每次都会静默丢掉代理）。桌面宿主重启=重启
app；自证信号是日志里的启动时间戳行。**重启后注意清单**：死线已落盘不丢
（已过期的自动取消）；
旧会话工具面不追溯刷新（开新会话）；绑定表落盘所以不用手动唤醒会话，但
宿主回收过的会话对象要靠扫描重新发现；注入器去重表清空（同键可能重发
一次，无害）。

**双 profile 组合差异速查**：web 无 agent-preset-registry 默认预置行（全局
注册即可见）；desktop 有（默认 standard，封闭清单制，修复段+豁免在档）。
桌面宿主日志不落盘（诊断走 dump-config 副本+会话转录）；web 宿主 stderr
落 `web.err.log`。

## 九、会话存储与 transcript 布局

| 宿主 | 会话转录 | 位置 |
|---|---|---|
| DSH web/桌面 | `session.v4.jsonl.zstd`（zstd 压缩 JSONL，逐事件一行：用户/模型/工具调用/工具结果/注入消息） | `~/.dsh/sessions/<路径化会话名>/session-<uuid>/` |
| zcode | sqlite 三表（session/message/part）+每条后台命令的 stdout 落盘 | `~/.zcode/cli/db/db.sqlite`、`~/.zcode/cli/exec/<会话id>/` |

判读会话 transcript 的实用规律：注入消息以 user 角色+spliced 标记出现在
回合边界；分块帧（chunk）不带时间戳，做时序过滤要用事件帧；会话头部的
`agentPreset` 字段=该会话加入的预置（工具面可见性以此为准）。

**什么落盘、重启丢什么**（两系统合表）：因子引擎的账本/审计种子/绑定表
落盘；死线也已落盘（2026-10-03 起，过期自动取消）；注入键表、待发定时器
是内存态（重启丢，见第五节）。投研系统
全部状态在仓库文件里，会话本身只在外部宿主的转录里。宿主进程死亡无转储
（历史上有过静默死亡无日志的事故夜）——所以 web 重启必须带 stderr 捕获，
出事才有尸检材料。

## 十、七问速答

1. **装了什么**——因子挖掘：四个 npm 包（服务/桥/工具/组合件）+pip -e 的
   Python 引擎；投研：什么都不装，仓库里的命令行程序+一个预置。
2. **在哪一层**——因子挖掘：宿主进程内（组合树两行）；投研：宿主进程外
   （每次命令调用即起即退）。
3. **模型看见什么**——因子挖掘：factor_* 工具面（桌面=预置封闭清单说了算）
   +注入的用户角色消息；投研：引擎命令输出+技能壳+persona。
4. **指令怎么送达**——因子挖掘：三通道（工具响应 loop 区/回合注入/指令
   文件），一次判断三次投放；投研：全拉取式（回执/工作单/审计门）。
5. **状态放哪**——因子挖掘：账本根+绑定表+死线（factor-drive-state.json）
   落盘；注入键表与待发定时器在内存；
   投研：全在仓库，宿主零状态。
6. **怎么升级**——TS 包升版本号重装 tgz；Python 改主树 pip -e 即生效；
   重启必须走 dshweb（带代理与 stderr）；重启丢死线、旧会话不追溯。
7. **三宿主差异**——web=无预置默认（全局注册即见）；桌面=预置封闭清单制
   （修复后预置持工具面+注入器，豁免在档）；zcode=不经宿主（桥 CLI 直连，
   最多吃通道三，注入器永远不可见）。
