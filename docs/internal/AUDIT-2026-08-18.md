## 1. 架构全景

```
DSH (桌面 agent)
  └─ tool-factor-mining（工具层，25 个 factor_* 工具；json 参数 string|object 归一化）
       └─ factor-mining（seam：纯类型 + 抽象服务，零依赖）
            └─ factor-mining-python（provider：spawn Python bridge 子进程，JSON-RPC 2.0 over stdio）
                 └─ bridge.py（26 个 dispatch 方法：路由 / 纪律层状态 / lockfile / 进度通知）
                      ├─ discipline.py（指纹三元组 / AST 签名 / 低效扫描 / 红旗+verdict）
                      ├─ factor/evaluate.py（IC/IC_IR/column-perm/beta/衰减/top-N/DSR/敏感性）
                      ├─ factor/causality.py（双方法前视检测 + 执行计时 + 非确定性双跑）
                      ├─ factor/audit.py（独立重算审计）
                      ├─ factor/memory_pool.py（有界双池 64/32 + .npy 数值指纹）
                      ├─ factor/random_gen.py（随机因子种子 + null 地形校准）
                      ├─ factor/ops.py（37 个向量化算子）
                      ├─ data/adapters.py（probe/config/校验/内存估算，820 行最大单模块）
                      ├─ worker.py（子进程隔离执行用户因子代码）
                      └─ state.py（trail/explored/search_paths/registry 落盘）
用户 stateRoot：data-config.json（约定路径+mtime 惰性重读）/ trail_engine.json / pool/{active,falsified}.json
              / pool/fp/*.npy / registry.json / test_lock.json / reports/ / backups/ / .lock
```

规模：Python 5007 行 / TS 1996 行 / 测试 1715 行（Python）+ e2e 320 行（TS）。

## 3. P0 — 立即修（3 个）

### P0-1 `factor_registry_submit` 工具层缺 `diagnosis` 参数 — DSH 端入册 100% 失败
- `ts/factor-mining/src/types.ts`：`RegistrySubmitRequest` 只有 `envId/source/name/signal`，**没有 diagnosis 字段**
- `ts/tool-factor-mining/src/index.ts:368-385`：execute() 只转发这 4 个字段
- `bridge.py:_registry_submit`：`if not isinstance(diagnosis, dict) or "ic_ir_train" not in diagnosis: raise BridgeError(-32602, ...)`
- **后果**：SKILL 第 6 步要求「入册时带上完整 evaluate 诊断」，但工具接口根本没有这个入口 → DSH 端每次入册都被 bridge 拒绝。
  receipt 防编造、铁律查重、red_flags 拒绝——整个批次 1a 的入册纪律在真实产品面上**不可达**。
  Python 测试直调 dispatch 传了 diagnosis，所以 54/54 全绿没暴露。
- **修法**：types.ts 加 `diagnosis?: JsonRecord` → tool parameters 声明 `diagnosis`（type: json）→ execute 转发。service 直通无需改。

### P0-2 部分显式三区分界被 auto 静默覆盖
- `data/adapters.py:637-647`：`explicit_regions = ("dev_end" in raw and "sel_end" in raw and ...)`
- 用户只填 `dev_end` 不填 `sel_end`（或反之）→ `explicit_regions=False` → auto 分支**无条件覆写两个分界**，用户显式值被静默丢弃，且 `regions_auto=True` 只标了 auto，不标「你填的那个被丢了」。
- **直接违反「三区划分由用户决定」的核心设计承诺**（这是用户本周期亲自拍板的协议）。
- **修法**：单边显式时保显式值、只 auto 补缺的一边，并加 `regions_auto: "partial"` 标记；或直接拒绝单边配置要求成对填写（更诚实）。

### P0-3 calibration 数值域零校验（horizon≤0 / cost_bps<0）
- `data/adapters.py` `resolve_calibration`（约 :102-127）只校验 frequency/execution 枚举，不校验数值域：
  - `horizon=0` → `_forward_returns` 语义崩坏（c[0]/o[1]）；负数 → 索引错
  - `cost_bps<0` → 负成本 = 交易倒贴钱，**任何垃圾因子在 top-N 净收益里都变盈利**
- **修法**：`horizon>0`、`cost_bps>=0`、`dev_end<sel_end`、日期格式 `pd.Timestamp` 试解析，全部在 config 写入/校验时拒绝（现在 dev_end 格式错误要拖到 load 才以 pandas 报错炸出）。

## 4. P1 — 应修（按危害排序，20 个）

### 统计正确性（影响数字可信度）

| # | 问题 | 位置 | 证据 |
|---|---|---|---|
| P1-1 | **DSR 门槛反保守**：`sr0 = (0.5**0.5)*(2·lnN)^0.5 = √(lnN)`，非 B-LdP 的 √(2lnN)，门槛低估 √2 倍；且 `0.5*erfc` 注释「双尾」实为单尾。方向 = 高估显著性 | `evaluate.py` `_deflated_sharpe_p` | 人工复核确认 |
| P1-2 | **block-bootstrap z 结构性死亡**：`z=(mu−stats.mean())/se`，circular bootstrap 分布中心就是样本均值 → z 恒≈0、p 恒≈1。topn 诊断里的 block_bootstrap 字段全是死数字（不进门控，但会误导读诊断的 agent） | `evaluate.py:152-168` | 人工复核确认；正确形式 `z=mu/se` |
| P1-3 | audit 的 Spearman 用 tie 失效的 footrule 公式 `1−6Σd²/(n(n²−1))`，evaluate 用 rank+corrcoef；有 tie 的因子（大量 0 值/一字板）两者系统性偏差 > TOL=1e-4 → **审计假 FAIL** | `audit.py:58-63` vs `evaluate.py:82-86` | |
| P1-4 | `ic_sample_every < horizon` 静默放行重叠 IC 窗 → 相邻 IC 正自相关 → IC_IR 通胀。**绕过「IC_IR 不重叠口径」铁律且无警告** | `env.py:44,53-54` | |
| P1-5 | net_annual 年化用 `annualization/horizon` 而实际换手频率是 `sample_step` → `ic_sample_every<horizon` 时年化低估 | `evaluate.py:480,482` | |
| P1-6 | 分钟口径 `annualization` 不随 `bars_per_day` 自动派生；用户设了 bars_per_day=48 忘设 annualization → 全部年化指标错 48 倍 | `env.py:42,46` | |
| P1-7 | causality 非确定性双跑对固定种子因子无效（`np.random.seed(42)` 两次同结果 → 检测恒 False） | `causality.py:30-35` | 二跑前 `np.random.seed(seed+1)` 可破 legacy API；default_rng 无法拦截需文档声明 |
| P1-8 | null 校准 n=50：p95 的 SE≈±10pp、p99 期望观测 0.5 个 = 纯噪声，但解读文本当精确阈值输出 | `random_gen.py:294,333-337` | |
